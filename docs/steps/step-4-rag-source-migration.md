# Step 4 — Secure RAG Source Migration

Date: 2026-10-12

## Outcome

The Secure RAG runtime source now lives inside the SentinelAI repository under
`backend/app/rag`. The migration is namespaced and intentionally inactive:
SentinelAI's existing API and conversation behavior have not been changed.

## Migrated components

- RAG configuration and asynchronous database helpers
- PDF validation, parsing, scanning, chunking, and ingestion pipeline
- Document, chunk, ACL, finding, and audit model definitions
- Embedding, hybrid retrieval, reranking, and document-scope validation
- Groq generation, prompt construction, and citation validation
- Input, retrieved-context, output, policy, and rate-limit guards
- Document, query, and retrieval service code
- Document, retrieval, and generation API schemas
- Existing RAG route implementations retained for later adapter work

The package contains 46 Python files, including the new package boundary file.

## Deliberately not migrated

- The standalone RAG FastAPI `main.py`
- The standalone RAG health and development-auth routes
- The standalone static `/admin` HTML/CSS/JavaScript dashboard
- RAG Alembic migrations
- Uploaded PDFs, model caches, environment files, and generated bytecode

These exclusions prevent a second application, identity authority, migration
history, or administrator frontend from being introduced into SentinelAI.

## Namespace isolation

All copied internal imports use `app.rag.*`. The moved package has no imports
back to the root Secure RAG application's `app.*` modules.

The moved routes are not included by SentinelAI `app.main`, so they cannot be
called until the authentication and database adapters are implemented.

## Dependency and configuration preparation

The SentinelAI backend requirement file now declares the RAG-specific runtime
libraries:

- asyncpg
- fastembed
- groq
- pgvector
- PyMuPDF
- pydantic-settings
- requests

The SentinelAI environment example now documents ingestion, retrieval,
reranking, Groq, and RAG rate-limit settings. Upload and embedding-cache paths
are excluded from Git.

## Temporary migration references

> Step 5 status: the temporary implementations described below have now been
> replaced by SentinelAI identity and database adapters. See
> `docs/steps/step-5-identity-database-integration.md` for the current design.

`backend/app/rag/auth` still contains the original standalone RAG JWT and role
implementation only as a reference for the next adapter step. It must not be
registered or used as a second production authentication system.

Likewise, the copied RAG model base and fixed access-role enum are not yet part
of SentinelAI's combined schema. The next database/authentication step must
replace them with SentinelAI user and role relationships before routes are
enabled.

## Next implementation gate

Create SentinelAI authentication adapters and the combined database models:

1. derive a RAG principal from SentinelAI's authenticated `User` and `Role`;
2. replace enum ACLs with `role_id` foreign keys;
3. link document uploads to SentinelAI `users.id`;
4. enable pgvector and add the RAG tables through the combined migration path;
5. keep all RAG routes disabled until those changes and their authorization
   tests pass.
