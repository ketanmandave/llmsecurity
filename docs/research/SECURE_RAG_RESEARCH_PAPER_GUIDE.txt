2. CENTRAL RESEARCH IDEA
------------------------

One-sentence description:
The proposed system combines retrieval-augmented generation with role-based
document permissions so that an authenticated user can retrieve and use only
the organizational information permitted for that user's current database
roles.

Problem statement:
Normal RAG systems can retrieve semantically relevant passages without checking
whether the requesting user is authorized to see the source document. In an
enterprise environment, this can expose confidential HR, management, finance,
or internal policy information. RAG applications also face prompt injection,
sensitive-data leakage, irrelevant retrieval, unsupported answers, and unsafe
output risks. A practical system therefore needs retrieval quality and security
controls to operate together rather than treating authorization as an
after-processing step.

Research gap to investigate:
Many publications evaluate RAG mainly for answer quality or retrieval quality.
Many access-control systems separately study user authorization. This project
investigates their integration: access restrictions are applied before and
inside retrieval, while document ingestion, retrieved context, generation,
citations, auditing, and document lifecycle are handled in one pipeline.

Do not claim that no previous system combines RAG and access control until a
systematic literature search confirms it. Write "this work investigates" or
"this work presents" instead of "this is the first".


3. PROPOSED CONTRIBUTIONS
-------------------------

Present these as contributions of the implemented prototype, not as globally
novel inventions unless the literature review proves novelty.

1. A document-ingestion pipeline for native-text PDF files that validates the
   upload, extracts text, scans content, chunks the document, generates dense
   embeddings, and stores chunks with document metadata and access roles.

2. Role-aware retrieval in which the server derives roles from an authenticated
   user and applies authorization constraints before inaccessible chunks can
   become LLM context.

3. Hybrid retrieval that combines dense-vector similarity, lexical matching,
   title relevance, relevance thresholds, and an optional cross-encoder
   reranker to reduce unrelated retrieval.

4. Grounded answer generation through Groq using the
   openai/gpt-oss-120b model, with citations linked to retrieved source chunks.

5. Layered controls around the RAG path, including authentication, rate
   limiting, prompt-risk checks, retrieved-context checks, response checks,
   audit records, and document activation/deletion controls.

6. An administrative interface for uploading documents, assigning access
   roles and classifications, inspecting document state, deactivating and
   reactivating documents, and permanently deleting documents and their vector
   chunks.


4. RESEARCH OBJECTIVES
----------------------

Primary objective:
To design and evaluate a secure enterprise RAG pipeline that preserves useful
retrieval while enforcing document access according to authenticated user
roles.

Specific objectives:
1. Build a reliable native-text PDF ingestion and vector-indexing workflow.
2. Enforce server-side document permissions during retrieval.
3. Improve relevance using hybrid ranking, reranking, and rejection thresholds.
4. Generate source-grounded answers with verifiable citations.
5. assess authorization correctness, retrieval quality, answer grounding,
   latency, and behavior on unrelated or adversarial queries.
6. Provide administrative lifecycle operations and auditable system behavior.


5. RESEARCH QUESTIONS AND OPTIONAL HYPOTHESES
---------------------------------------------

RQ1: How accurately does the system retrieve relevant chunks for authorized
users?

RQ2: Does the retrieval pipeline prevent users from receiving chunks belonging
to roles they do not possess?

RQ3: Does hybrid retrieval with reranking improve Precision@K, Recall@K, and
MRR compared with dense-vector-only retrieval?

RQ4: How reliably does the system return an empty result or an insufficient-
evidence response for unrelated questions?

RQ5: How accurately do answer citations support the claims made by the LLM?

RQ6: What latency overhead is introduced by authorization filtering, hybrid
ranking, security checks, reranking, and generation?

Optional hypotheses, to be tested rather than assumed:
H1: Hybrid retrieval plus reranking improves ranking quality over vector-only
retrieval on the same labelled test set.
H2: Database-backed role filtering produces zero unauthorized chunk disclosures
in the defined authorization test suite.
H3: Minimum-score and relative-score filtering improve empty-result accuracy
for unrelated queries, with a measurable recall trade-off.


6. SCOPE AND BOUNDARIES OF THE CURRENT SYSTEM
---------------------------------------------

Included in the current implementation:
- One organization; tenant ID is intentionally not used.
- Native-text PDF upload and extraction.
- Document-level allowed-role assignment by an administrator.
- JWT/session authentication integrated with SentinelAI database users.
- Server-side role resolution and role-aware chunk retrieval.
- Dense embeddings using BAAI/bge-small-en-v1.5 with 384 dimensions.
- PostgreSQL with the pgvector extension.
- Hybrid vector, lexical, and document-title signals.
- Optional cross-encoder reranking.
- Relevance thresholds and unrelated-query rejection.
- Groq-hosted openai/gpt-oss-120b answer generation.
- Citations to retrieved document chunks.
- Input, retrieved-context, and output security checks.
- Redis-backed supporting services such as rate limiting.
- Audit information and administrator document lifecycle operations.
- React/Vite frontend and FastAPI backend.

Not currently implemented; place these only in Limitations or Future Work:
- OCR for scanned PDFs.
- Image understanding or multimodal RAG.
- Multi-tenant isolation.
- Attribute-based access control (ABAC).
- A learned or agentic query router that automatically chooses general LLM
  chat versus RAG.
- A formal guarantee against every prompt-injection attack.
- Automatic proof that every generated sentence is factually correct.

8.3 Threat Model and Security Requirements
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Define these explicitly before describing defenses.

Assets:
- Original organizational documents.
- Extracted chunks and embeddings.
- User identity and roles.
- Retrieved context.
- Generated answers and citations.
- Audit records and credentials.

Actors:
- Authorized employee.
- HR or manager with additional permissions.
- Administrator.
- Authenticated but unauthorized user.
- Malicious user attempting prompt injection or data extraction.
- Malicious or compromised document containing hidden instructions.

Trust boundaries:
- Browser to backend API.
- Backend to PostgreSQL/pgvector.
- Backend to Redis.
- Backend to external Groq model service.
- Administrator upload boundary.

Security requirements:
SR1. The server, not the client, must determine effective roles.
SR2. Inaccessible documents must not enter retrieved LLM context.
SR3. Deactivated or deleted documents must not be retrievable.
SR4. Suspicious input and retrieved content must be detected or handled by

8.5 Methodology: Document Ingestion
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Describe the actual sequence:

1. An authenticated administrator uploads a PDF and supplies a display name,
   allowed roles, and a classification.
2. The API validates the file type, PDF structure, request fields, roles, and
   configured size/page constraints.
3. Native text is extracted with PyMuPDF. A file without usable embedded text
   is rejected because OCR is outside the current scope.
4. Extracted text is inspected by configured injection/sensitive-content
   detectors and policy rules.
5. Text is divided into overlapping chunks. The current configuration uses a
   target of 450 words and an overlap of 75 words.
6. Chunk embeddings are generated by BAAI/bge-small-en-v1.5. Each vector has
   384 dimensions.
7. The chunks, embeddings, document identifiers, page information, roles,
   classification, and status are stored in PostgreSQL/pgvector.
8. The document becomes retrievable only if ingestion succeeds and its status
   is active.

Explain the chunk-size choice as an engineering configuration, not a universal
optimum. Experimentally compare at least two or three chunk configurations if
the paper claims that the chosen value is optimal.

8.6 Methodology: Authentication and Authorization
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. A user authenticates through SentinelAI.
2. The backend validates the token/session and resolves the current user.
3. Effective roles are obtained from server-controlled database records.
4. Any roles supplied in a query body are ignored or rejected; the browser is
   not an authority for permissions.
5. Retrieval considers only active documents whose allowed-role set intersects
   the authenticated user's roles.
6. Requested document IDs are also checked for existence and accessibility.

Explain JWT as a token format and cite [R5], but clarify that JWT alone does not
provide authorization. Authorization depends on validation, server policy, and
current database role state.

8.7 Methodology: Authorized Retrieval and Ranking
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
The current system obtains an authorized candidate set and combines several
relevance signals.

Signals:
- Vector similarity between the query and chunk embedding.
- Lexical overlap between the query and chunk text.
- Title relevance between the query and document name/title.
- Optional cross-encoder relevance score.

Current final scoring configuration:

With reranking:
FinalScore = 0.45(RerankerScore) + 0.35(VectorScore)
             + 0.12(LexicalScore) + 0.08(TitleScore)

Without reranking:
FinalScore = 0.65(VectorScore) + 0.22(LexicalScore)
             + 0.13(TitleScore)

Current retrieval configuration:
- Candidate count: 20
- Default returned top_k: 5
- Minimum initial retrieval score: 0.20
- Minimum final score: 0.35
- Relative score margin: 0.12

Describe these as prototype hyperparameters. In a research paper, report how
they were selected (development set, grid search, or engineering judgement) and
avoid tuning them on the final test set.

8.8 Methodology: Generation and Citation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
1. The system constructs an LLM prompt using only authorized, accepted chunks.
2. Source labels and metadata are included with the evidence.
3. Groq openai/gpt-oss-120b generates an answer constrained by the supplied
   evidence and instructions.
4. Returned citation identifiers are validated against the chunks actually
   provided to the generator.
5. If evidence is absent or insufficient, the desired behavior is to decline
   to make a document-grounded claim rather than invent an answer.
6. The response passes through output security checks before delivery.

Distinguish these terms in the paper:
- Citation validity: the cited source identifier exists in retrieved context.
- Citation correctness/support: the cited passage actually supports the claim.
- Citation completeness: important factual claims have citations.
Identifier validation alone does not prove semantic support.

8.9 Methodology: Administrative Lifecycle
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
- Active: document can participate in authorized retrieval.
- Inactive: metadata remains, but the document is excluded from retrieval.
- Reactivated: the document is again eligible under its existing permissions.
- Permanently deleted: document records and vector chunks are removed according
  to the implemented deletion transaction and no longer appear in the admin UI.

Verify deletion using both an API/database check and a retrieval attempt. Avoid
claiming secure physical erasure from disk unless storage-level erasure was
specifically implemented and tested.

9.3 Metrics and formulas
~~~~~~~~~~~~~~~~~~~~~~~~

Precision@K:
Precision@K = Number of relevant items in top K / K

State whether an "item" is a document or a chunk. Do not mix both definitions
in one result table.

Recall@K:
Recall@K = Number of relevant items in top K /
           Total number of labelled relevant items

Mean Reciprocal Rank (MRR):
MRR = (1/N) * SUM(1 / rank of first relevant result)
Use 0 for a query with no relevant result returned.

Empty-result accuracy:
Number of unrelated/no-evidence queries correctly returning no accepted context
divided by the total number of unrelated/no-evidence queries.

Authorization accuracy:
Number of authorization test cases with the correct allow/deny outcome divided
by the total authorization test cases.

Also report unauthorized disclosure count separately. A high percentage can
hide a serious single disclosure.

Citation support precision:
Number of evaluated citations whose passages support the associated claims
divided by total evaluated citations.

Citation completeness:
Number of externally verifiable answer claims that contain a supporting citation
divided by total externally verifiable answer claims.

Answer correctness:
Use a predefined rubric, human evaluation, or an independently validated judge.
If an LLM judge is used, report its model, prompt, temperature, failure handling,
and human-validation sample. Do not label an unvalidated LLM score as ground
truth.

Security metrics:
- Unauthorized disclosure count.
- Attack detection rate = detected labelled attacks / total labelled attacks.
- False-positive rate = benign cases incorrectly blocked / total benign cases.
- False-negative rate = malicious cases missed / total malicious cases.

Performance metrics:
- Ingestion time per document/page/chunk.
- Retrieval latency: median (p50) and 95th percentile (p95).
- Generation latency: p50 and p95.
- End-to-end response latency: p50 and p95.
- Index/storage size if relevant.

Always report sample count with every percentage.

14. LIMITATIONS AND THREATS TO VALIDITY
---------------------------------------

System limitations:
- Only PDFs with usable embedded text are supported; scanned PDFs require OCR
  and are intentionally rejected.
- Roles are document-level; sections within one document do not have independent
  permissions unless they are uploaded separately or the schema is extended.
- RBAC cannot express all context-dependent rules such as location, device,
  working hours, or case assignment.
- Detector rules/models can have false positives and false negatives.
- External generation introduces provider availability, privacy, and latency
  considerations.
- Dense retrieval and reranking remain probabilistic and domain-dependent.
- Citation ID validation does not guarantee claim support.
- One-company design does not demonstrate tenant isolation.

Internal validity threats:
- Hyperparameters may be overfitted to the evaluation documents.
- Human relevance labels can be subjective.
- Cached embeddings or warmed models can bias latency results.
- LLM output nondeterminism can change answer scores.

External validity threats:
- A small college/enterprise-style dataset may not generalize to legal, medical,
  multilingual, or very large collections.
- Synthetic security attacks may not represent adaptive real attackers.
- Results for one embedding model and one generator may not transfer to others.

Construct validity threats:
- Precision/Recall measure retrieval, not complete answer correctness.
- "Authorization accuracy" must be based on explicit policy cases.
- An automatic LLM judge may prefer certain writing styles or model families.

Reproducibility threats:
- External hosted model versions may change.
- Dependency and model versions must be pinned and reported.
- Random seeds and generation settings must be recorded where supported.
